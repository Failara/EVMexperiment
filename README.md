# Експеримент зі зіставлення адрес EVM

Реалізація на C#/.NET 10 алгоритмів M1–M6, локальна підготовка даних Ethereum, перевірки коректності та запуск експериментів в ізольованих процесах. Цільова версія SDK: **10.0.400**. Під час вимірювань RPC та доступ до Інтернету не використовуються.

**Поточний стан:** підготовлено програмний пакет для кваліфікаційних перевірок із реальними даними та сирими результатами. Повне наукове дослідження E0–E6 ще не виконано. Перед використанням цих вимірювань у публікації прочитайте `EXPERIMENT_STATUS.md`. Файл `configs/final-experiment.json` фіксує невелике кваліфікаційне навантаження, а не повне дослідження.

## Збирання та тести

Виконуйте команди з кореня репозиторію у PowerShell за наявності встановленого .NET 10 SDK:

```powershell
dotnet restore
dotnet build -c Release
dotnet test -c Release
```

Попередження трактуються як помилки. Тести написані на xUnit; виробничі проєкти не мають зовнішніх залежностей пакетів. NuGet потрібен для першого відновлення залежностей тестів, але подальша підготовка даних і вимірювання виконуються локально.

## Дані та відтворюваність

Включений архів містить блоки основної мережі Ethereum **20,000,000–20,000,019**, завантажені з публічного endpoint лише для читання `https://ethereum-rpc.publicnode.com`. Архів містить 2 882 записи транзакцій, 5 760 спостережень адрес і 3 168 різних реальних адрес. Витягуються лише поля транзакції `from` і ненульове `to`. Адреси створення контрактів і теми подій не виводяться припущеннями. Номери блоків і хеші батьківських блоків перевіряються.

Імпорт відповідає [Ethereum Execution API](https://ethereum.github.io/execution-apis/api/methods/eth_getBlockByNumber/). Файл `data/raw/source.json` містить відомості про походження даних; сирі відповіді збережено. Розбиття 30/10/60 виконується за межами транзакцій в початковому порядку; перші дві межі округлюються вниз. Під час кваліфікації вимірювальна частина не використовується для налаштування контролера.

Повторно підготуйте всі файли збереженого архіву без доступу до Інтернету:

```powershell
./scripts/prepare-data.ps1
```

Щоб завантажити інший архів:

```powershell
./scripts/fetch-data.ps1 -BlockFrom 20000000 -BlockTo 20000019
```

Для іншого архіву чи seed використовуйте окрему копію репозиторію або нові імена файлів. Вхідні дані вже отриманих результатів мають залишатися доступними з початковими хешами. Команда завантаження зберігає наявні файли блоків і не перезаписує їх.

Бінарні формати використовують порядок байтів little-endian і не мають заголовка:

- `watchlist.bin`: послідовність адрес по 20 байтів.
- `queries.bin`: 8-байтовий знаковий sequence, 8-байтовий знаковий event ID, адреса на 20 байтів (36 байтів на запис).
- `updates.csv`: sequence, timestamp_ns, operation, address_hex. Оновлення з sequence не більшим за номер наступного запиту застосовуються перед цим запитом.
- `events.jsonl.zst`: стандартний кадр Zstandard із сирими блоками. Він сумісний зі звичайними декодерами zstd; сирі блоки не потребують додаткового native runtime.

Щоб зберігати розширений архів у практичному обсязі, відповіді блоків записуються у форматі `.json.gz`; нормалізатор також приймає початкові звичайні файли `.json`. Потоки запитів для симуляцій за розкладом зберігаються як `.bin.gz`, а маніфести містять хеш стиснутих байтів, які читає runner.

Формування watchlist є детермінованим. Воно вибирає спостережені адреси для наближення до заданої початкової частки влучань, а решту заповнює реальними адресами, відсутніми у вибраній частині даних. Неможливі розміри watchlist і частки влучань відхиляються з явною помилкою. Операції оновлення використовують коректні Add/Remove. Маніфест сценарію записує початкову частку влучань і частку під час відтворення; оновлення можуть змінити останню.

Щоб підготувати інший допустимий сценарій:

```powershell
dotnet src/EvmMatching.Runner/bin/Release/net10.0/EvmMatching.Runner.dll prepare measurement my-scenario 100 0.05 10 1 240001
```

Аргументи: частина даних, назва сценарію, розмір watchlist, цільова початкова частка влучань, номінальна частота оновлень, номінальна тривалість розкладу та seed. Номінальні частота й тривалість визначають кількість оновлень і часові мітки в їх метаданих. **Політика скінченного відтворення використовує sequence, а не часові мітки.** Фактична частота оновлень записується окремо. Для контрольованого розкладу надходження запитів і оновлень використовуйте описану нижче політику scheduled.

## Пілотний запуск і серії

Скрипти збирають проєкт, запускають повний набір перевірок коректності й лише після цього починають вимірювання:

```powershell
./scripts/pilot.ps1
./scripts/run-series.ps1 -Plan configs/qualification-plan.json
```

Для включених ідентифікаторів серій результати вже існують. Ці команди навмисно відмовляються їх перезаписувати. Щоб повторити кваліфікацію, спочатку створіть план із новим ID:

```powershell
$plan = Get-Content configs/qualification-plan.json -Raw | ConvertFrom-Json
$plan.seriesId = 'qualification_replay_01'
$plan | ConvertTo-Json -Depth 10 | Set-Content configs/qualification-replay.json
./scripts/run-series.ps1 -Plan configs/qualification-replay.json
```

План містить шляхи до конфігурацій сценаріїв, методи, кількість незалежних повторів (типово 30) і seed для порядку методів. Порядок методів рандомізується та зберігається до початку виконання. Кожен запуск відбувається в новому дочірньому процесі; налаштований режим GC встановлюється до запуску CLR. Для порівняння спільними є хеші навантаження, seed, режим GC і кількість робочих потоків. Серія зупиняється після першої помилки, зберігаючи попередні каталоги.

Для одного запуску спершу задайте його конфігурації новий ID серії:

```powershell
dotnet src/EvmMatching.Runner/bin/Release/net10.0/EvmMatching.Runner.dll run configs/my-run.json
```

`run` запускає ізольований дочірній процес; `run-one` — внутрішня точка входу для дочірнього процесу. Перевірочне відтворення обчислює точні очікувані відповіді до вимірювання, а під час вимірюваного відтворення кожна відповідь порівнюється з попередньо обчисленим оракулом. Розбіжність зупиняє запуск. Маркер `SUCCESS` отримують лише повні результати з коректними відповідями.

Для калібрування елементарних операцій використовуйте новий ID:

```powershell
dotnet src/EvmMatching.Runner/bin/Release/net10.0/EvmMatching.Runner.dll calibrate calibration_replay_01
```

E0 зберігає окремі сирі тривалості пошуку H/Fd/Fs/Hd, вставлення та видалення в H/Fd, побудови статичного фільтра, перемикання режиму й фонового перебудування. Це коротке калібрування в одному процесі, а не завершена серія E0 із 30 повторами.

## Реалізація та методика вимірювання

- `Address20` — упакований тип значення розміром 20 байтів. Пошук не виконує розбір адрес, перетворення на рядки чи виділення масивів адрес.
- M1 використовує точну `HashSet<Address20>`.
- M2 використовує counting Bloom filter із сімома хешами й 32-бітними лічильниками. Видалення виконується лише після підтвердження членства через H. Вичерпання місткості спричиняє помилку до публікації адреси. Це дозволена інструкцією альтернатива Cuckoo-фільтру, без його реалізації.
- M3 використовує незмінний статичний Bloom filter разом із Hd. Нова версія створюється поза блокуванням запису, після чого узгоджується з усіма проміжними оновленнями та публікується разом із Hd під одним блокуванням. Адреси, видалені зі snapshot, можуть залишатися безпечними хибнопозитивними збігами до перебудування. Одночасно може працювати лише одна перебудова.
- M4 зберігає H, Fd, Fs і Hd, вибирає проби в усіх режимах і застосовує обмеження ресурсів, гістерезис послідовних кандидатів, а також оцінки окупності перемикання й перебудування. Оцінка користі перебудування порівнює спостережену вартість S2 з калібруванням чистого snapshot з урахуванням поточної частки влучань. Вимірюються початкові й наступні витрати на побудову. Перед стартом побудови також перевіряється оцінка пікової тимчасової пам’яті. Усі збережені фільтри враховуються в оцінці бюджету пам’яті кожного режиму.
- M5 використовує один інтервал гістерезису. M6 використовує фіксований період перебудування. В іншому обидва методи повторюють поведінку M4. Причини й тривалості рішень, перемикань і перебудувань зберігаються у `controller_events.json`.
- Робочі потоки запитів виконують детерміновані пакети, розділені бар’єрами оновлень. Це зберігає порядок оновлень і запитів, який використовує оракул; окремі тести перевіряють справді конкурентну роботу читачів і записувачів.
- Вхідні дані, створення оракула, запуск процесу, початкові структури й прогрів не входять до вимірювання. Вимірювана частина включає диспетчеризацію, витрати stopwatch/гістограми, порівняння відповідей і адаптивні тіньові проби.
- Скінченний набір даних відтворюється повними проходами, доки не буде досягнуто мінімальної сумарної тривалості вимірювання. Відновлення стану між проходами не входить до часу пропускної здатності. Ця політика підходить для кваліфікації. Політика scheduled виконує одне безперервне відтворення без відновлення стану.
- Усі затримки запитів потрапляють до обмеженої гістограми з кошиками 1/16 октави. Вказані процентилі є верхніми межами кошиків. Пам’ять — це RSS/піковий working set процесу; виділені байти — це виділення процесу під час вимірювання, вони включають відновлення стану між проходами. Фонові перебудови завершуються до позначення запуску як успішного.
- Інтервали визначаються за сумарним часом алгоритму, останній інтервал може бути неповним. Часові мітки подій фонових завдань відраховуються за wall clock від скидання лічильника; перебудови, завершені після останнього інтервалу запитів, слід перевіряти в журналі подій.

## Перевірка та передавання результатів

```powershell
./scripts/validate-results.ps1
./scripts/handoff.ps1
```

Аудит перевіряє обов’язкові файли, відсутність фінальних помилок, хеші входів, кількість і межі інтервалів та спільні параметри порівняння. Передавання автоматично перелічує каталоги, успішні/невдалі/неповні запуски, хеш версії збірки й SHA-256 для джерел, скриптів, конфігурацій, даних і сирих результатів. Воно не створює підсумкових таблиць чи графіків.

Каталоги результатів розташовані у `results/raw/<seriesId>/<experiment>/<scenario>/<runId>/`. Каталог без `SUCCESS` є неповним або невдалим. Збережіть його, усуньте причину й використайте новий ID серії, якщо змінюються код, параметри чи входи. Раптове завершення процесу може залишити неповний каталог без `failure.json`; handoff явно позначає такий стан.

Попередні пілоти зі скінченним відтворенням і кваліфікація мають старіші хеші збірок; їхні результати збережено. Запуски запланованого дослідження записують власні хеші збірок у `environment.json`. Пакет не містить приватних ключів, облікових даних RPC чи обов’язкових абсолютних локальних шляхів.

## Автоматизація повного дослідження за розкладом

У `STUDY_PROTOCOL.md` описані попередньо зареєстроване дослідницьке питання, гіпотези, сітка факторів, політика вимірювання, план статистичного аналізу та обмеження.

Політика `scheduled` виконує одне безперервне відтворення, задає темп надходження запитів і оновлень монотонним годинником та зберігає стан між межами профілів. Загальна пропускна здатність обчислюється за wall-clock часом, включно з очікуванням за розкладом. Затримка вимірює час обслуговування запиту; максимальне відставання від розкладу звітується окремо, щоб було видно перевантаження. Робочі потоки запитів зберігають детерміновані бар’єри оновлень. Окрім запланованої частоти, записується фактично досягнута частота оновлень.

Симуляція навантаження повторно вибирає лише пари адреса/подія, що вже присутні у вибраній часовій частині даних. Вона змінює частку влучань, порядок подій і умови оновлення, зберігаючи реальні адреси й вихідні ID подій. Оновлення почергово виконують допустиме видалення та додавання; частка видалень дорівнює 0.5 з урахуванням округлення, а W змінюється не більш ніж на одиницю. Для кожного змодельованого запиту час надходження детерміновано визначається його індексом і частотою запитів. Частота запитів має бути не меншою за максимальну частоту оновлень.

Скорочена сітка запускає всю автоматизацію на включеному невеликому архіві:

```powershell
./scripts/new-study.ps1 -SeriesId scheduled_demo_01 -Smoke
./scripts/run-study.ps1 -Plan configs/scheduled_demo_01-plan.json
```

Включений `scheduled_smoke_v3` використовує новий ID серії, 11 сценаріїв E1–E6, один повтор і одне коротке калібрування E0. Це програмний smoke-набір, а не повне наукове дослідження.

Щоб підготувати більший архів, не перегенеровуючи й не змінюючи збережені кваліфікаційні навантаження, завантажте дані в `data/raw/` і окремо нормалізуйте архів:

```powershell
./scripts/fetch-data.ps1 -Rpc 'https://eth-mainnet.g.alchemy.com/public' -BlockFrom 20000000 -BlockTo 20021999
./scripts/normalize-archive.ps1
```

Скрипт нормалізації зберігає розширений маніфест і частини даних у `data/fullstudy/processed/`, залишає початкові входи кваліфікації на місці та зберігає їхні метадані джерела у `data/archive/qualification_20block/`. Калібрування й змодельовані навантаження повного дослідження читають дані з розширеного каталогу.

Спочатку виконайте короткий повнорозмірний пілот на частинах tuning і validation. Він порівнює M1–M4 за W=1,000,000 із запланованою частотою запитів та перевіряє стабільність прогріву, коректність і пам’ять. Пілот відокремлений від фінальної серії:

```powershell
./scripts/pilot-full-study.ps1
```

Перевірте метрики інтервалів пілота та маркери `SUCCESS`. Потім створіть повний план. Генерація плану створює лише конфігурації й хешовані входи для відтворення за розкладом; вона не запускає фінальну серію вимірювань:

```powershell
./scripts/new-study.ps1 -SeriesId full_study_01
```

Після перевірки плану та резервування достатнього часу виконайте повну сітку:

```powershell
./scripts/run-study.ps1 -Plan configs/full_study_01-plan.json
```

Додавайте `-IncludeFiveMillion` лише тоді, коли дані й пам’ять дозволяють таку додаткову точку. Генератор перевіряє кількість реальних адрес перед підготовкою сценаріїв. Без цього параметра сітці потрібно понад один мільйон різних реальних адрес. Повний запуск має 30 повторів, 30 секунд прогріву й 300 секунд вимірювання для кожного сценарію, із запланованою частотою надходження запитів 100 000/с. Перед фінальною серією наукових вимірювань підтвердьте тривалості й ресурсні межі на даних tuning/validation. Під час підготовки повний запуск навмисно не стартує.

Поточна повна сітка містить 25 сценаріїв E1–E5 (усі шість методів) і 23 сценарії чутливості E6 (M4–M6), тобто 6 570 вимірюваних запусків за 30 повторів. Самі вікна вимірювань становлять 1 971 000 секунд (приблизно 22.8 дня), без урахування прогріву, перевірочного відтворення, запуску процесів та E0. Заплануйте резервування машини відповідно. Повністю однакові навантаження використовують ті самі хешовані входи, але кожна конфігурація має власну ідентичність сценарію.

Сітка включає всі запитані розміри watchlist до одного мільйона, десять часток влучань, п’ять частот оновлень, профілі P1→P2→P3→P4→P1, кількість робочих потоків до числа логічних ядер і окремі точки аналізу чутливості. E6 виконується для M4–M6; інші сценарії — для M1–M6. P1 — рідкі влучання без оновлень, P2 — часті влучання без оновлень, P3 — рідкі влучання зі змінами, P4 — часті влучання зі змінами. Кожен профіль займає одну п’яту сценарію. Точні визначення та хеші всіх входів зберігаються до початку виконання. E0 запускається в окремих процесах після основної сітки й включається до handoff.

`prepare-data.ps1` також повторно створює всі збережені `*-simulation.json`, перевіряє, що хеші даних не змінилися, і зберігає зафіксовані параметри експерименту. Лише цей крок можна виконати окремо скриптом `scripts/rebuild-simulations.ps1`.

Щоб запакувати перевірені джерела, входи, сирі результати та маніфест handoff в один переносний архів:

```powershell
./scripts/package.ps1
```

Архів створюється як `artifacts/EvmAddressExperiment.zip`. Кеші збірки, бінарні файли й локальні QA-файли виключаються. Наявні архіви не перезаписуються; перед повторним пакуванням перенесіть старий архів в інше місце.
